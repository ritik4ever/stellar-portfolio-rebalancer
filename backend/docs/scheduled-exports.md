# Scheduled Portfolio Exports

Users can opt a portfolio into a recurring emailed CSV export (#1411). Weekly is the
only frequency today; the storage and job shapes leave room for more.

## Endpoints

All three require JWT auth and portfolio ownership.

| Method | Path | Purpose |
| --- | --- | --- |
| `PUT` | `/api/v1/portfolio/:id/export-schedule` | Create or update the schedule |
| `GET` | `/api/v1/portfolio/:id/export-schedule` | Read the current schedule |
| `DELETE` | `/api/v1/portfolio/:id/export-schedule` | Cancel the schedule |

`PUT` body:

```jsonc
{
  "frequency": "weekly",              // optional, defaults to "weekly"
  "emailAddress": "user@example.com", // required
  "enabled": true,                    // optional, defaults to true
  "firstRunAt": "2026-09-07T06:00:00Z" // optional, defaults to one week out
}
```

Scheduling requires active consent, matching the on-demand export endpoint.

## How a run works

1. The `scheduled-export` repeatable job fires **Mondays at 06:00 UTC**.
2. The worker claims every enabled schedule whose `next_run_at` cursor is in the past —
   so a tick missed during downtime is caught up on the following run rather than
   skipped, and one repeatable job covers any number of users.
3. Each schedule's CSV is generated by `getPortfolioExport(portfolioId, 'csv')` — the
   same function the on-demand export endpoint calls. Generation logic is reused, not
   duplicated.
4. The CSV is attached to an email sent through the existing notification email
   provider (`notificationService.sendEmailWithAttachment`).
5. The outcome (`success` / `failed`, plus any error) is recorded and the cursor moves
   forward one week — **whether or not the run succeeded**, so a persistently failing
   schedule cannot wedge the sweep into retrying forever.

If the portfolio has been deleted, the schedule is disabled and the run reported as
`skipped` rather than failing on every tick.

Email delivery failures are loud by design: `sendEmailWithAttachment` throws when SMTP
is unconfigured, so the schedule records a real failure instead of silently doing
nothing. SMTP configuration is the usual `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS`.

## Storage

`export_schedules`, one row per portfolio:

| Column | Notes |
| --- | --- |
| `portfolio_id` | primary key |
| `user_address` | owner |
| `frequency` / `format` | `weekly` / `csv` today |
| `email_address` | delivery target |
| `enabled` | opt-out without losing the row |
| `next_run_at` | scheduling cursor |
| `last_run_at`, `last_status`, `last_error` | last outcome, surfaced to the user |
